一句话结论

DeepSeek 不是不用 HBM/SSD，而是：

  1. 先把上下文 KV Cache 压到极小（算法 + 低精度）；
  2. 再把冷数据放到 Host DRAM / SSD（只让 GPU 常驻热工作集）。

读法提示：「减少对 SSD 的依赖」更准确是指：同样 Agent / 前缀缓存业务下，需要的 SSD 容量、带宽与命中成本显著下降；不是废弃 SSD。

先分清两件事：HBM 压力从哪来

压力来源 是什么 DeepSeek 主要手段
KV Cache（上下文记忆） 长上下文 / Agent 多轮时随 token 线性膨胀 MLA → DSA → CSA/HCA + 低精度 + HiCache/HiSparse
模型参数 / 外部记忆表 大模型权重、Engram N-gram 表 MoE 稀疏激活 + Engram 确定性查找 offload

宣传口径里的「减少 HBM/SSD 依赖」主要指 KV Cache；Engram 是并行的「参数/知识表」故事。

机制 1：从根上压缩 KV（最关键）

1) MLA（V2 / V3）：头维度低秩压缩

  • 不存完整多头 K/V，只缓存低维 latent。
  • DeepSeek-V3 量级约 ~70 KB/token，远低于同代大模型。
  • 直接降低 HBM 容量与带宽 压力。

2) DSA（V3.2-Exp）：稀疏注意力

  • DeepSeek Sparse Attention：长上下文只对关键 token 做细粒度注意力。
  • 算力开销下降；但 latent cache 仍随长度增长，因此后续出现 ESS / HiSparse 等 offload 方案。

3) CSA + HCA（V4 核心）

机制 压缩比 作用
CSA（Compressed Sparse Attention） 约 4:1 先按块压缩，再用 Lightning Indexer 做 top-k 精读
HCA（Heavily Compressed Attention） 约 128:1 重度压缩后做稠密「全局摘要」注意力
SWA 局部窗口 最近若干原始 token，保证近因细节

再叠加存储精度：多数 KV 用 FP8，RoPE 相关用 BF16，CSA indexer 用 FP4。

公开解读给出的量级：V4-Pro 相对 V3.2 约 10% KV / 27% 单 token FLOPs；V4-Flash 约 7% KV / 10% FLOPs；相对传统 GQA+BF16 可到约 2% KV cache。

对 HBM：同样 1M 上下文，显存常驻 KV 小一个数量级以上。
对 SSD：若用磁盘做 prefix / 跨请求缓存，落盘体积也按同样比例缩小——这是「SSD 需求降到 1/8」的核心合理解释。

机制 2：服务侧分层存储（HBM ← DRAM ← SSD）

Prefill：HiCache（含 L3 Storage / SSD）

  1. L1 GPU HBM：热 prefix / 当前工作集
  2. L2 Host DRAM：更大可复用前缀
  3. L3 Storage（常落 NVMe/SSD）：跨请求、跨会话冷 prefix

目标：Agent / RAG 多轮提高前缀命中，少做重复 prefill。KV 越小 → 同样 SSD 容量能缓存更多会话 → 等效「更少依赖大 SSD」。

Decode：HiSparse（主要卸到 Host）

  • GPU 只留固定大小的 hot buffer（如数千 token 槽位）。
  • 完整 C4（CSA 压缩历史）放 CPU pinned mirror。
  • 每步 indexer 选出 top-k，miss 才 Host→GPU 拷回。
  • PD 分离时，Prefill 甚至可经 RDMA 直写 Decode 的 Host 池，避开 Decode GPU 尖峰。
HBM（热工作集） ↑ on-demand swap-in / prefetch DRAM（完整压缩历史 / prefix mirror） ↑ cold prefix / 跨会话复用 SSD / Storage（L3 冷层）

机制 3：Engram——减少「参数级」HBM 依赖

官方论文 Conditional Memory via Scalable Lookup：

  • 用确定性 N-gram 查找，把静态知识表与动态计算解耦。
  • 推理时大表可放 Host DRAM，用前序层计算做 prefetch + overlap PCIe。
  • 利用 Zipf：热项进 HBM/DRAM，长尾进 NVMe SSD。
  • 实验：把 100B 参数表全放 host，吞吐损失约 2.8%。
Engram 是 主动利用 SSD 作为廉价冷层 来换 HBM；与 V4.1「减少 SSD 需求」（因为 KV 更小）是不同维度，不要混为一谈。

版本演进：谁在解决什么

V2/V3 MLA → 单 token KV 变小（HBM） ↓ V3.2 DSA → 长上下文稀疏算力 + 为分层卸载创造条件 ↓ V4 CSA+HCA+低精度 → KV 再压一个数量级（HBM + 盘上缓存体积） + HiCache/HiSparse → 热冷分层（HBM / DRAM / SSD） ↓ V4.1-Flash 公告 → 相对上代：HBM 1/4，SSD 1/8；相对初代 ~437× Causal Encoder–Decoder（输入激活 8B / 输出 16B，552B MoE）

关于 DeepSeek-V4.1-Flash

  • 约 552B MoE，原生多模态，API 模型名 deepseek-flash。
  • 采用新的 Causal Encoder–Decoder 非对称结构：输入激活约 8B，输出激活约 16B。
  • 官方结果陈述：相对上一代，KV Cache 对 HBM 需求降至 1/4、对 SSD 需求降至 1/8。
  • 机制上应视为 V4 压缩路线的产品化 / 结构升级；4.1 专属完整 tech report 目前不如 V4 清晰，细节仍以官方后续文档为准。

社区里的 FlashMemory / LSA（如 arXiv:2606.09079）是在 V4 上进一步「只召回关键 CSA chunk」的第三方/合作研究，不是 DeepSeek 4.1 官方同名产品。

可落地理解框架

减少 HBM 依赖 ├─ 算法压缩（MLA / CSA / HCA / 低精度） └─ 运行时只留 hot set（HiSparse / 稀疏 top-k） 减少 SSD 依赖 ├─ 同样缓存占用的字节数变小（压缩后的 KV） └─ 更多冷数据可放 DRAM；SSD 只存真正跨会话长尾
